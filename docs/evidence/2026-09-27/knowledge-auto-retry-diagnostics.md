# 知识库导入失败与自动恢复：本地证据

来源：用户提供的 `mobile-agent-diagnostics(7).zip`，SHA-256 `f712c3ac5ec3f69a7fe75c897ae05f981c14f2ce9e9178c5bb812b8a096d62e8`。只读取 manifest 与 `current.ndjson`；原始诊断未复制进仓库。构建记录为 `1cf142f`、schema 26，日志时间范围 2026-09-27 09:07:25–09:47:30 UTC，均为同一 pid 855。

## 本次失败原因

23 次视觉派发中，18 次有 `vision_success`，4 次成为 `vision_unknown`，最后 1 次截至打包时仍在途。四次 UNKNOWN 均约在派发后 180 秒出现：09:13:51→09:16:51、09:16:55→09:19:55、09:20:13→09:23:13、09:34:09→09:37:09 UTC。应用普通 `HttpClient` 当时的 request/socket timeout 都是 180,000 毫秒，与时间间隔精确吻合，因此客户端传输超时是最强的可检验根因。日志未保存服务端是否完成处理或计费，也未保存这四次的完整 HTTP 异常正文；不能把 UNKNOWN 解释为服务端未处理。

日志另有一次图片能力探测 `partial`/HTTP 4xx；同一配置的真实视觉处理多次成功，说明“不支持图片输入”的探测结论是误判。旧探测图片仅 1×1 像素，可能被多模态图片处理器拒绝；日志没有每项探测的响应正文，不能把图片尺寸写为已经证实的唯一原因。模型资料与当次请求显示为 `Qwen/Qwen3.8-27B`。

本包未显示进程死亡：所有事件属于同一 pid。进程死亡后接续能力由持久状态与模拟中断测试验证，不能把本包当成真实后台杀进程验收。人工状态切换和批次 worker 重启记录解释了用户为何需要反复点击重试。

## 本地修复与验证

- 视觉专用传输超时改为 600 秒；图片探测用经解码验证为左红右蓝的 128×128 PNG，泛化 4xx 归为未知而不误报“不支持”。旧探测记录需重新执行能力探测才能更新。
- 批次对 UNKNOWN、超时、限流与暂时断网最多六次自动重试；保存 UNKNOWN 和 attempt，已成功页不重发；WorkManager 指数退避，进程恢复重排可恢复批次。系统中断不再被记为用户取消；显式暂停/取消仍生效。
- 三个处理 lane 与 schema v27 三个持久派发槽一致；API Embedding 仍单路，SQLite/index 写入串行，未授权的可能含图批次先单路越过授权检查。启动时也结清失败、暂停、阻塞和取消批次留下的在途派发槽，不自动重启用户已停止的批次。
- JVM 覆盖三路真实重叠、六次耗尽、成功页复用、进程恢复、派发槽释放、取消与恢复竞态，以及 v26→v27 迁移。`data:sqlite:test` 333/333、`shared:provider-api:test` 210/210、`:app-android:testDebugUnitTest` 132/132、Android 编译及 `licenseGuard` 在本地通过；真实设备长响应、后台杀进程与 300–500 文件性能尚未验收。独立只读复核对当前改动给出 PASS，未发现剩余 P0–P2 问题；复核未独立重跑测试。
