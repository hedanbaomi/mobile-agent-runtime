# ADR 0026：运行时限只管准入，在途回复完整接收

日期：2026-10-06（Asia/Taipei）。状态：本地实现，独立只读审阅见本轮证据，待真机验收。修订 [ADR-0010](0010-conversation-context-compaction.md) 第 8 条与技术实现方案中“总运行 180 秒”的执行语义；预算数值不变。

2026-10-07 数值修订见 [ADR-0031](0031-skill-bindings-and-adaptive-context.md)：默认准入时限 1800 秒，可配置，Python broker 读取同一持久预算；停滞默认 180 秒和本 ADR 的准入/在途/取消/未知结果语义保持。

## 背景

用户 v1.1.0 诊断包：Run 于 04:32:55.36 开始，04:35:55.485 变为 `UNKNOWN_OUTCOME`，正好 180.1 秒；此前 17 轮模型请求、16 次工具全部 HTTP 200，终止前 0.05 秒仍在持续收到推理增量，没有用户取消、断网或 watchdog 记录。原因是 `AgentRuntime` 用 `withTimeoutOrNull(remainingMs)` 包住已派发的模型流（包括摘要请求）和工具调用，并在流内到期时抛出 `BUDGET_CANCEL`；仍在到达的回复被截断，按已派发未知结果处理，界面显示“已取消接收……外部结果未知”。用户要求：已经开始的回复无论如何都要完整接收显示。

## 决定

- `RunBudget.maxRuntimeMs` 改为准入截止：到期后不再开始新的模型请求、摘要请求、工具调用或审批后派发，Run 以 `BUDGET_EXHAUSTED`（stopReason `time`）结束；UI 提示已收到的回复完整保留、未发起新请求，可继续提问。
- 已派发的模型流、摘要流和工具调用不再受截止时间截断，只在自身终态、调用方取消或停滞超时时结束。新增 `RunBudget.stallTimeoutMs`（默认 180 秒）：模型流连续这么久既没有事件也没有传输分块（SSE 诊断，含工具参数和隐藏推理阶段），或单次工具调用这么久仍未返回，判为 `UNKNOWN_OUTCOME`，保留部分响应，不自动重放；下游处理事件的时间不计为停滞，中途传输异常前已收到的内容按序送达。RunTools 与 Python 工具同样只在准入时检查截止，已启动进程沿用自身 30 秒上限；Python broker 每个请求在入口检查一次截止（过期返回 `RESOURCE_LIMIT`），已准入的请求（如仍在接收的 model.invoke）不被截止截断，撤权、终态 Run 与绑定变化仍立即拒绝。
- 完整收到的回复先按其自身终态结算（COMPLETED/FAILED）；截止检查只决定是否继续执行该回复请求的工具和下一轮，并在每次主请求派发前复查（含摘要被拒后回退原文的路径）。截止后才收完的合法摘要仍持久化为 SUCCEEDED 供后续复用，但本轮不再发起主请求。
- 等待用户审批仍受剩余截止时间约束；到期不派发 `approve`，与原 `APPROVAL_EXPIRED` 语义一致。
- 聊天 watchdog 由固定“截止 + 60 秒”改为空闲判定：运行事件和每个传输分块都算进展，使用单调时钟，超过 `max(2 × stallTimeoutMs, maxRuntimeMs) + 60 秒` 无进展才停止等待；持续到达的长回复或长摘要不触发。
- OpenAI Chat Completions 与 Responses 流式请求只解除 Ktor 总请求时长上限，连接 15 秒与 socket 空闲 180 秒保持，断流仍会失败。非流式、Embedding、视觉、MCP、搜索客户端不变。

## 替代方案及代价

直接调大总时限仍会在更晚时刻截断在途回复，不满足需求。完全取消时限会让工具循环无界。仅发送 SSE 保活而永不产生内容的异常流不会触发停滞判定，只能由用户取消，作为已知残余风险记录。当前方案下，最坏总时长约为截止时间加一次完整回复及其一批工具执行；单次请求和单个工具仍受停滞超时、工具自身限额与 HTTP 空闲超时约束，模型/工具次数上限不变。截止到期后已观测但未执行的工具调用保留为观测记录，不执行也不重放。

## 验证与影响

### 2026-10-06 合并前审查补充

- 主请求的 `RequestPrepared` 消费和摘要的 `DISPATCHED` 检查点写入均可能挂起；两者返回后必须在真正接触 Provider 前再次检查截止。未派发的主请求以时间预算结束；已登记 DISPATCHED 但确定尚未调用 Provider 的摘要转为 FAILED（现有存储状态机允许），不标为未知、不计虚构用量、不自动重发。
- 流停滞检测按 `stallTimeoutMs` 周期采样进展。检测延迟最多约两个采样窗，慢消费者处理时间不计入停滞；默认每窗 180 秒。watchdog 预留两个采样窗加 60 秒，避免先于 Runtime 的未知结果结算。SSE 进展按完整传输行计，不承诺任意单个网络字节均可延长等待。
- 工具本身的确定完成结果完整保留；其后的本地图像附件读取属于新准备工作，仍受剩余准入时间和来源授权限制。附件未完成时停止后续派发，不伪造已发送图片。
- 审查新增两项确定性回归：请求预览消费越过截止、摘要派发检查点写入越过截止。两项均在补检前失败，补检后零 Provider 派发。

- shared agent-runtime 72/72：截止期间回复完整送达且 COMPLETED、慢速但持续的流完整接收、仅有传输分块的长静默阶段不判停滞、下游慢处理不判停滞、中途传输异常保留部分内容并 UNKNOWN、截止后不执行工具也不发起下一轮、摘要被拒或截止后收完都不再派发主请求、工具越过截止保留结果后停止、审批等待仍受截止约束且不派发、模型/工具/摘要停滞为 UNKNOWN 且不重放；首批 5 项在修复前代码上失败。
- provider-api 275/275：两类流式请求仅总请求时长为无限，socket/连接超时保持 180 秒/15 秒；未安装 HttpTimeout 的客户端不受影响。
- Android 单元 253/253；API34 模拟器聊天/所有权/压缩/审批/工作区/Python/RunTools 相关设备测试 70 项通过；主线程回归、RunTools 截止回归与 Python broker 跨截止回归在修复前代码上各自失败（后者旧行为为 UNKNOWN_OUTCOME）。
- 真实 Provider 长回复、物理设备和 OEM 网络栈未验收。
